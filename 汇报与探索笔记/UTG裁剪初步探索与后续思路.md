# UTG 裁剪初步探索与后续思路（探索性笔记 · 非最终交付方案）

> **定位说明**：本文档仅记录在无损动态数据采集过程中对「鸿蒙端侧 UTG 裁剪」的**初步摸底观察与后续设计思路**，供接手同事参考。**本项裁剪任务尚未完成**——下文仅测算了原始 JSON 的体积与字面字段保留情况，**尚未**在真实鸿蒙端侧开展下游检测模型/分类器的端到端 F1、误报率（FPR）、端侧时延与内存消融验证。

---

## 一、为什么要保留无损数据再做裁剪？

目前采集的 `dynamic_utg_418/` 故意不做前置丢弃，完整保留了每步原图截屏、Android XML、转换后的鸿蒙 `uitest dumpLayout` JSON 和窗口/通知遥测，目的是为后续同事做裁剪对照实验留出「无损基线」。

在已跑出的 302 款可运行样本上摸底，单个应用的完整无损鸿蒙 JSON 平均约 **616 KB（8.5 页、304 个控件节点）**——直接送端侧模型明显过重，确实需要裁剪。

---

## 二、提供给后续同事的四条 UTG 裁剪探索思路（待实验定型）

### 思路 1：页面级锚点窗口裁剪（减少捕获页数）
- **初步想法**：无需在应用每次页面切换时都抓 Layout；可尝试以「进入系统无障碍设置页 / 应用信息受限设置页」为触发锚点，仅保留 **跳前诱导页（`t-1`）+ 无障碍列表页（`t`）+ 跳后探针（`+2s`）+ 服务详情页 + 拒权回退页**（实测可从平均 8.5 页降至 3.3 页，体积减半）。
- **待后续验证**：对「先退桌面再弹浮层（如 `EventBot`）」或多步图文教学应用，跳前仅回溯 1 页（`K=1`）是否足够，还是需要 `K=2`？

### 思路 2：控件树节点与属性裁剪（压缩单页 JSON）
- **初步想法**：
  - **节点级**：剪除无文本/无 `description` 且不可点击/不可勾选的纯布局壳容器（`Column`/`Row`/`Stack`），并在系统无障碍列表页过滤固定系统样板项（如字体大小、放大手势、深色主题等）；
  - **属性级**：OpenHarmony `uitest dumpLayout` 单控件有 30 项属性，初步观察用于安全研判的核心字段约 8 项（`type`、`text`、`description`、`bounds`、`clickable`、`checkable`、`checked`、`id` + 窗口级 `bundleName`/`abilityName`）。
- **摸底数据（仅供量级参考，非最终效果）**：仅按上述规则做格式压缩时，单应用均值体积可从约 **616 KB → ~5.4 KB**（若转紧凑元组则 ~2.6 KB），跳前文本与服务详情字面保留率为 100%。
- **待后续验证**：剪除位置排版细节和不可交互容器后，是否会影响识别「高仿系统设置 UI 结构」或「透明遮罩点击劫持」？需用下游检测模型做真实准确率/误报率消融。

### 思路 3：跨通道微上下文补盲（避免“只裁 Layout 漏掉隐蔽攻击”）
- **关键摸底发现**：仅看控件树 JSON 时，**约 89% 的「跳后系统页顶部通知横幅压栈」信号会丢失**（如 `Hook`、`Ermac`、`Hydra`、`RuMMS`、`GodFather` 不申请悬浮窗而是靠通知横幅在设置页顶部发指令）；此外，国内「银联会议/中银会议」等带外语音诈骗在 App 界面内几乎没有恐吓文字。
- **建议方向**：同事设计裁剪协议时，可考虑在裁剪后的 Layout 之外附加一小段跨通道上下文（目标应用活跃通知摘要、悬浮窗计数、冷启动至跳设置步长、通话/录屏并发状态），并在真实端侧测试其对检出率与隐私合规的影响。

### 思路 4：纯布局 vs 视觉截图的按需分流
- **观察**：约 20% 恶意样本使用纯图片/GIF 或空白 WebView 承载诱导内容，纯 JSON 文本稀疏。
- **建议方向**：可探索「默认仅传轻量裁剪 Layout，仅当跳前页文本极少且含大图/WebView 时才按需补送单帧截屏或触发端侧轻量 OCR」的分流策略，在端侧算力与召回率之间找最优平衡点。
