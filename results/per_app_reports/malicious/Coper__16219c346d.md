## 分析结论（定向核验）

**核心判断：静态视界内无法还原“无障碍引导流程”，因为引导 UI 根本不在 DEX 里。**

1. **DEX 是空壳，只有一个类。** 全包反编译仅得 [zON1MlSbIrj](<resource-unit:#1.dex1 code:com.ublocked47tallcloud.zON1MlSbIrj>)（Application）。Manifest 中声明的 `gQ7ju`(LAUNCHER)、`vtiE8xJsNyR`、`rwhPH5HS1`、`jvuxavS`(无障碍服务)、`ldORI3R`(通知监听) 等组件类在该 DEX 内均不存在；对 `accessibility` / `settings` / `http` / `Enable this service` 的全包文本检索零命中。
2. **真实逻辑在原生层解密释放。** `<clinit>` 只做 `System.loadLibrary("mgawuggXqFM7j")`，[attachBaseContext](<resource-unit:#1.dex1 code:com.ublocked47tallcloud.zON1MlSbIrj#attachBaseContext>) 立刻调 JNI `ts9h3ytl4j(Context)`。`libmgawuggXqFM7j.so` 导出 `WrpClass::replace_loader / unpack_dynlib / get_AES / get_salt / get_DGA / write_so / load_so` 与整套 `ARC4::setKey/ksa/prga/encrypt`，即：ARC4 解密内层 so → 落盘 → dlopen → 替换 ClassLoader。这是标准“一阶段壳 + 二阶段 DEX/so 载荷”结构，静态预筛的 `加壳=False` 属于误判（DEX 层面确无加固特征，但载荷已整体移出 DEX）。
3. **诱导载体不可静态定位。** 冷启动 Activity、弹窗、WebView、悬浮窗、`ACTION_ACCESSIBILITY_SETTINGS` 跳转点全部只可能存在于解密后的载荷中。唯一静态可见的引导文本是系统无障碍列表里的 `android:description`（"Enable this service to protect your device."），属系统页承载，不是应用自绘引导。
4. **无障碍请求的权限面极宽。** [tvyradg.xml](<resource-unit:#1 file:res/xml/tvyradg.xml>) 配置 `typeAllMask` + `canRetrieveWindowContent` + `canPerformGestures` + `canTakeScreenshot` + `flagRetrieveInteractiveWindows`，配合 READ_SMS/SEND_SMS、CALL_PHONE、QUERY_ALL_PACKAGES、WRITE_SETTINGS、设备管理员 receiver、开机/USER_PRESENT 广播，符合 Coper 系银行木马能力组合；但“如何一步步引导”这一具体问题的答案不在静态范围内。
5. **UTG 检测策略必须改为运行期锚定。** 静态找不到跳转点，因此不能在代码层预置 Hook 点，只能以“无障碍服务被启用/系统设置页被拉起/悬浮窗出现”作为运行期触发信号。
